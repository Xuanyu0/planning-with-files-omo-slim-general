# 利用文档，搭配 OMO-slim 进行开发规划的通用版本

## 设计思想：

* AI 做任何**无人**监督的决定后必须确认，人类需要在有书面契约的情况下做审查。
* 利用好 Git 和硬盘上的文件
* AI Agent 执行流程透明，可理解

## 使用前提

### 适用此模式的场景

- 新增功能模块
- 新设计模式引入
- 旧代码重构（中大型）
- 危险的 BUG 修复（可能破坏旧有功能）

### 绝对不要用的场景

- 逻辑简单清晰的问题
- 单文件修改或双文件机械迁移（小型重构）
- 快速查询
- 代码问答

## 四种核心文件

| 文件 | 规则 |
|------|------|
| 总纲 | 与 `步骤/`、`发现/`、`提示词/` 同级，文件名为 00-总纲.md |
| 步骤 | `步骤/{编号}-{名称}.md`，发现文档与之同名 |
| 发现 | `发现/{编号}-{名称}.md` |
| 提示词 | `提示词/{编号}-{名称}/`下，目录以步骤编号开头 |

例子：
```markdown
docs/开发文档/<阶段名>/
├── 00-总纲.md
├── 步骤/
│   └── 04-<步骤名>.md          ← 步骤文档
├── 发现/
│   └── 04-<步骤名>.md          ← 发现文档（文件名与步骤文档相同）
└── 提示词/
    └── 04-<步骤名>/
        └── 4.6-<提示词名>.md     ← 提示词文档
```


### 总纲文档

* 定义：步骤文件的统领，阶段性对应的总纲文件
* 功能：
  * `dev-status.py` 脚本用于对开发文档的定位与处理
  * 人类对总体进度的把控

### 步骤文件

* 定义：在具体开发任务前 AI 与用户共同商讨过后制定的文件，交付给用户看的
* 内容解释：
  * 步骤的目标：一句话描述完成后系统的状态
  * 初评难度：分为不确定度 / 算法复杂度 / 工作量三行、三个维度
  * 影响范围
    * 重构类：完整画出新旧架构的对比图，以字符画形式呈现
    * BUG 修复类：定位所有需要执行修改的文件
    * 新功能开发类：指出新功能的所属架构地位，并给出对应新文件所处的目录结构
  * 待确定决策：开始写代码之前需要向用户提问并确定的决策（同样不要涉及开发细节，那是提示词的职责）
  * 已确定决策：已经定下来的代码规则，作为后面写提示词的参考
* 注意：
  * 步骤文档是给人看的，是用来对齐用户和你的想法的，所以不需要写一些无关紧要的实现细节
  * 用图，或者自然语言写
  * 不需要写验收标准
  * 这个文件不是执行手册
  * 初次书写的合理范围应该在60行~150行，超过200行，首先自查一遍是否混入提示词细节
  * 写作时难度/影响范围按子步骤，决策按步骤，目标按步骤+子目标按子步骤

### 发现文件

* 定义：在开发过程中完全由 AI 顺手发现并记录的文件，既可以给Agent看，也可以给人类工程师看
* 创建时机：在开发过程中 subagent 发现任何问题或改进点时，立即按步骤创建或更新此文件
* 具体内容：
  * @发现者（fixer/cleaner/oracle）
  * 历史遗留 BUG：不是本次开发阶段产生的 BUG，但在本阶段中发现了
  * 改进项
  * 不确定事项：
    * 定义：开发过程中临时决策，并且已经写出代码，而自己没有太大把握，需要用户确认的决策
    * 记录问题内容 + 具体影响 + 状态标记（待确认 / 已确认）+ 建议
* 发现文件与步骤规划文件的记录优先级：
  * 优先在发现文件中记录 BUG 与优化项

### 提示词文件

* 定义：由@orchestrator 交付给@fixer /@designer的主要提示词，是执行阶段的输入契约，是给 Agent 执行契约与详细执行方案
* 具体内容（书写时按此顺序）：
  * **当前状态**：可以简述当前的问题以及对应的文件下的代码状态，为 Agent 指明问题方向
  * 架构变更（可选）：若涉及架构调整，用字符画呈现。
  * 具体子任务：进一步说明每个子任务需要干什么
  * 新增/修改文件：以表格的格式列出所有涉及文件，每个文件附带简要职责说明。
  * 不确定事项（可选）：本次 提示词 书写过程中产生的不确定事项。
  * 变更边界：明确禁止修改的文件、模块、函数。这是契约的红线。
  * **验收标准**：对应核心任务的每一项制定执行者/审查者可自行验证的完成条件列表。无验收标准的提示词不得交付执行。
  * subagent task 的返回内容要求。

#### 关于 task 返回值

编排者收到 @fixer 结果后：
* 确认自检清单完整性（所有修复项均已打勾或说明未完成原因）

编排者收到 @oracle 审查结果后：
* 审查全通过 → 进入更新文档阶段
* 审查不通过 → 按回流建议派原执行者重做或回规划修 提示词
* 有不通过并且非不确定项 → 按回流建议派原执行者重做或回规划
* 发现报告归入发现文档，编排者复核分类后写入

## 典型工作流

### 基本框架

```
    载入 skill
  → 开发启动协议

  → 用户指明方向
  → (探索 & 厘清现状) / 与用户讨论 / Web 搜索已有设计
  → session 内给出更加详细的设计方案

  → 撰写步骤文档
  → 用户确认（文档）
  → 撰写提示词文件
  → 用户确认（可选）

  → 执行 & 简化（可选） & 验证& 更新发现文档(重复执行)

  → 用户检查（代码）

  → 拟提交 & 用户确认
  → 执行 commit & 更新步骤文档 & 总纲文档（可选）

  → 反思（可选）
```
注1：没有画出回流
注2：只有用户明确说明“继续”类的提示词后才能执行（如执行，提交）。因为修改后用户可能还会进行多处修正
注3：“&”表示连续串行步骤，而不需要用户监督
注4："/"表示根据实际需要，灵活改变步骤方法

### 工作流的核心内容

* 讨论：
  * 目标：得到详细，明确的**功能需求**，确保你将要实现和是用户想要的完全一致
  * 方法论：
    * 讨论**不过多**涉及代码细节
    * 不确定的功能需求一定要询问。一次只询问一个问题，可以同时说说你的建议
    * 给出最终完整，详细的功能需求前，否则一定不要进入下一步写正式文档
  * 讨论结果输出：session 内一个更详细，有更多细节考量的设计方案
    * 用自然语言陈述
    * 可以用字符画阐述
* 规划与编写文档
  * 产出：步骤文档 / 提示词文档
    * 步骤文档写在对应开发阶段的 `步骤/` 子目录下，提示词文档写在对应开发阶段的 `提示词/` 子目录下，作为单独文件
    * 提示词文档也是贯穿执行与验证的契约。用户确认，执行，验证阶段共用同一份
* 用户确认
  * 用户确认后进入执行
  * 默认等待用户确认
* 执行
  * 执行期间各 specialist 报告的发现由 @orchestrator 实时收集，执行完后立即更新发现文档
* 简化
  * 读取对象：提示词文档 + git diff + 项目根目录级 CLAUDE.md / AGENT.md
  * 执行者：@cleaner
  * 不确定应不应该改或者清理 → 向上报告
* 验证
  * 读取对象：提示词文档 + 发现文档 + git diff + 项目根目录级 CLAUDE.md / AGENT.md
  * 执行者：@oracle
  * 读取对象：代码
  * 传入@fixer 执行阶段时的**同一份提示词文档**作为审查契约
  * 审查不通过 → 回@Orchestrator原委派对象（@fixer/@designer）执行；提示词 本身有误 → 回规划
* 用户检查
  * @orchestrator 暂停，等待用户检查代码
  * 步骤文档 + 发现文档一并呈现，检查发现文档为可选
  * 用户确认发现项 → 发现文档对应条目状态改为"已确认"
  * 用户要求调整 → 回对应阶段
* 提交
  * 用户明确许可后执行 git commit
  * **禁止**未经用户许可执行 git commit
* 更新开发文档
  * 操作对象：步骤文档 + 发现文档
  * 执行者：@orchestrator
  * 删除临时实现细节，只保留目标与关键产出摘要，并引用对应的 commit 提交
* 反思
  * 目标：优化 Skill 
  * 回顾上下文窗口，反思这次任务执行时出现的失误或者顺利执行的经验
  * 在 session 中告知用户即可

### 其他注意事项

#### 处理子代理的空值返回：

* 至少对那个没有返回值的子代理重试一次。不行的话再向上报告此次异常

#### 分派任务时直接引用已经编写好的提示词文档地址！

* 分派具体任务给 subagent 时不要重新完整的写一份提示词
* 包括 @designer，@fixer，@cleaner，@oracle
* 否则  subagent 的表现可能会欠佳，而且费 token

#### 发现文档的更新时机

* 每当 subagent 完成任务并上报时就记录

## 开发启动协议

**每次开始开发的事，按顺序执行：**

1. `git log --oneline -10` + `git diff --stat` — 了解整体进度和未提交改动
2. 利用 `glob` 工具查找项目已有的 `00-总纲.md` 文件的文件路径
3. 询问用户
    1. 如果只定位到一个总纲文件，跳过询问用户这个阶段
    2. 如果用户没有进一步指令，向用户展示当前已有的总纲文件（如果没有，请告知用户应该怎么做；）
    3. 如果用户有进一步指令，根据指令推断需要使用的总纲文件，如果不确定找到了，如实告知
4. 执行 `python3 .opencode/skills/planning-with-files-omo-slim-general/scripts/dev-status.py <总纲文件路径>` — 交叉验证步骤状态（活跃步骤、脏标记、待确认发现项）
5. 根据 dev-status.py 输出的 `🔥` 步骤，read 对应的步骤文档和发现文档

此序列确保：不用盲目遍历文件，先拿到全局视图，再精确 read 当前活跃的文件。

## 提示词契约

默认规则：没有触发词 → 停在当前阶段，不推进，并询问用户意图。
提示词组合：表示连续执行，不需要停下来，如“执行，简化，验证”或“执行，验证”（这就代表不包括简化）

* 讨论下吧/你怎么看 -> 和用户进行讨论
* 写总纲/步骤/发现文档 -> 进入规划阶段，撰写对应名称的文档（不多做）
* 执行 -> 进入执行阶段
* 简化 -> 进入简化阶段
* 验证 -> 进入验证阶段
* 提交 -> 拟提交代码，等待用户确认
* 反思 -> 进行反思（可选）

然后载入 skill 后，第一件事是按照你的理解复述自己会怎么执行这个工作流（即使用户有其他指示）

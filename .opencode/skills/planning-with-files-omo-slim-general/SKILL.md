# 利用文档，搭配 OMO-slim 进行开发规划的通用版本

## 设计思想：

* AI 做任何**无人**监督的决定后必须确认，人类需要在有书面契约的情况下做审查。
* 利用好 Git 和硬盘上的文件
* AI Agent 执行流程透明，可理解

## 使用前提

### 适用此模式的场景

- 新增功能模块
- 新设计模式引入
- 旧代码重构（中大型）
- 危险的 BUG 修复（可能破坏旧有功能）

### 绝对不要用的场景

- 逻辑简单清晰的问题
- 单文件修改或双文件机械迁移（小型重构）
- 快速查询
- 代码问答

## 四种核心文件

| 文件 | 包含的内容 | 必要规则 |
|------|------| ------| 
| 总纲 | 对应阶段的总体路线图、核心思想、步骤总表 | 与 `步骤/`、`发现/`、`提示词/` 同级，文件名为 00-总纲.md |
| 步骤 | 步骤划分、完成标志、当前进度 | `步骤/{编号}-{名称}.md`，发现文档与之同名 |
| 发现 | 历史遗留BUG、可以改进的地方、不确定项、相关报告 | `发现/{编号}-{名称}.md` |
| 提示词 | 功能需求、验收标准、scope guard、交互规则 | `提示词/{编号}-{名称}/`下，目录以步骤编号开头 |

例子：
```markdown
docs/开发文档/<阶段名>/
├── 00-总纲.md
├── 步骤/
│   └── 04-<步骤名>.md          ← 步骤文档
├── 发现/
│   └── 04-<步骤名>.md          ← 发现文档（文件名与步骤文档相同）
└── 提示词/
    └── 04-<步骤名>/
        └── 4.6-<提示词名>.md     ← 提示词文档
```


### 总纲文档

* 定义：步骤文件的统领，阶段性对应的总纲文件
* 功能：
  * `dev-status.sh` 脚本用于对开发文档的定位与处理
  * 人类对总体进度的把控

### 步骤文件

* 定义：在具体开发任务前 AI 与用户共同商讨过后制定的文件
* （每步）具体内容：
  * 步骤目标简述
  * 步骤收益/代价评估简述（可选）
  * 初评难度：分为不确定度 / 算法复杂度 / 工作量三行、三个维度
  * **核心任务**：本次任务需要完成的关键功能点，每个点简要说明做什么。
  * 每个步骤的完成标志：人类工程师不需要写代码就可以立马就做的验证行为
  * 影响范围
    * 重构类：完整画出新旧架构的对比图，以字符画形式呈现
    * BUG 修复类：定位所有需要执行修改的文件
    * 新功能开发类：指出新功能的所属架构地位，并给出对应新文件所处的目录结构
  * 待确定决策：开始写代码之前需要用户确定的决策
  * 已确定决策：已经定下来的事（直接陈述，不再讨论）

### 发现文件

* 定义：在开发过程中完全由 AI 顺手发现并记录的文件
* 创建时机：在开发过程中发现任何问题或改进点时，立即按步骤创建或更新此文件
* 具体内容：
  * 历史遗留 BUG：不是本次开发阶段产生的 BUG，但在本阶段中发现了
  * 改进项
    * 代码结构不合理
    * 代码可读性差
    * 代码可以简化
  * 不确定事项：
    * 定义：开发过程中临时决策，并且已经写出代码，而自己没有太大把握，需要用户确认的决策
    * 如：
      * 自己临时决策的架构设计，但不确定是否合理
      * 猜测某个用户对产品的使用意图
      * 对自己写的代码质量某一些地方没有信心
    * 记录问题内容 + 具体影响 + 状态标记（待确认 / 已确认）+ 建议
* 发现文件与步骤规划文件的记录优先级：
  * 优先在发现文件中记录 BUG 与优化项

### 提示词文件

* 定义：由@orchestrator 交付给@fixer /@designer的主要提示词，是执行阶段的输入契约。
* 与步骤文档的关系：一个是适合给人类工程师定位与阅读的大致规划，一个主要是给 Agent 执行契约与详细执行方案。
* 编写时需要指出一下内容拓展自步骤文档，便于人工确认：
  * 核心任务 -> 具体子任务
  * 影响范围 -> 变更边界、新增/修改文件
* 具体内容（书写时按此顺序）：
  * **当前状态**：可以简述当前的问题以及对应的文件下的代码状态，为 Agent 指明问题方向
  * 架构变更（可选）：若涉及架构调整，用字符画呈现。
  * 具体子任务：进一步说明每个子任务需要干什么
  * **新增/修改文件**：以列表的格式列出所有涉及文件，每个文件附带简要职责说明。
  * 不确定事项（可选）：本次 提示词 书写过程中产生的不确定事项。
  * **变更边界**：明确禁止修改的文件、模块、函数。这是契约的红线。
  * **验收标准**：对应核心任务的每一项制定执行者/审查者可自行验证的完成条件列表。无验收标准的提示词不得交付执行。
  * subagent task 的返回内容要求。

#### 关于 task 返回值

同一份 提示词 传给 @fixer 作为实现指令、传给 @oracle 作为审查契约。

@fixer 和 @oracle 的返回值格式已通过项目级 append 提示词注入到各自 agent（`fixer_append.md`、`oracle_append.md`），编排者只需关注接收后的处理流程：

编排者收到 @fixer 结果后：
* 确认自检清单完整性（所有修复项均已打勾或说明未完成原因）

编排者收到 @oracle 审查结果后：
* 审查全通过 → 进入更新文档阶段
* 审查不通过 → 按回流建议派原执行者重做或回规划修 提示词
* 有不通过并且非不确定项 → 按回流建议派原执行者重做或回规划
* 发现报告归入发现文档，编排者复核分类后写入


## 典型工作流

### 基本框架

```
    载入 skill
  → 开发启动协议
  → 用户指明方向
  → (探索 & 厘清现状) / 与用户探讨

  → 撰写步骤文档
  → 用户确认（文档）
  → 撰写提示词文件
  → 用户确认（可选）

  → 执行 & 简化（可选） & 验证（必选）
  → 撰写发现文档

  → 用户检查（代码）

  → 拟提交 & 用户确认
  → 执行 commit & 更新步骤文档 & 总纲文档（可选）

  → 反思（可选）
```
注1：没有画出回流
注2：只有用户明确说明“继续”类的提示词后才能执行（如执行，提交）。因为修改和用户会可能会进行多处修正
注3：“&”表示连续串行步骤，而不需要用户监督
注4："/"表示根据实际需要，灵活改变步骤方法

### 工作流的具体内容

* 规划与编写提示词文档
  * 操作对象：步骤文档
  * 执行者：@orchestrator（结构决策不委托）
  * 前置探查（按需，@orchestrator 缺乏上下文时触发）：
    * @explorer 探查代码现状与依赖
    * @librarian 查外部资料
  * 产出：步骤文档 + 提示词文档
    * 步骤文档写在对应开发阶段的 `步骤/` 子目录下，提示词文档写在对应开发阶段的 `提示词/` 子目录下，作为单独文件
    * 提示词文档也是贯穿执行与验证的契约。用户确认，执行，验证阶段共用同一份
  * 注意判断决策是否具有产品语义后果。如果有，可以在步骤规划中单开一个"待确定"区，供用户阅读。
* 用户确认
  * @orchestrator 呈现本次提示词，暂停等待用户确认
  * 用户确认后进入执行；用户要求调整则回规划
  * **禁止**未经确认直接进入执行
* 执行
  * 操作对象：代码（少数情况下可能是文档）
  * 机械实现 → @fixer
  * UI/UX 设计/实现 → @designer
    * 判断标准：改动涉及用户可见的视觉元素（布局、颜色、间距、动效、通知、浮层、错误展示位置）时，走 @designer
    * 纯逻辑改动（类型定义、状态管理、数据流、非渲染的计算逻辑）走 @fixer
  * 边做边决策的任务**不得**委托，@orchestrator 自行实现
  * 发现文档在此阶段创建，执行期间各 specialist 报告的发现由 @orchestrator 实时收集
* 简化
  * 操作对象：代码
  * 执行者：@simplifier
  * 简化明确不通过 → 回@Orchestrator重新安排原有执行者（@fixer/@designer）执行；不确定应不应该简化 → 向上报告
* 验证
  * 读取对象：提示词文档 + git diff + 开发文档
  * 执行者：@oracle
  * 读取对象：代码
  * 代码审查（传入@fixer 执行阶段时的**同一份提示词文档**作为审查契约）
    * 符合提示词契约
      * 检查是否满足最小实现，功能实现**不得**超过提示词要求
      * 检查是否删除任何历史代码，除非 提示词 明确要求
      * 若遇到不确定事项
        * 向 @orchestrator 报告
    * 符合既有架构规则
      * 检查是否满足CLAUDE.md中架构规则
      * 检查是否满足其他开发文档中架构规则
  * 审查不通过 → 回@Orchestrator原委派对象（@fixer/@designer）执行；提示词 本身有误 → 回规划
* 初步更新文档
  * 操作对象：步骤文档 + 发现文档
  * 执行者：@orchestrator（唯一写入者，不委托）
  * 步骤文档：标记状态（`⏳` → `✅`），删除临时实施细节，只保留关键产出
  * 发现文档：归档执行和验证期间收集的发现，分类（bug / 改进 / 不确定），状态标记为"待确认"
* 用户确认
  * @orchestrator 呈现更新后的步骤文档 + 发现文档，暂停等待用户确认
  * 用户确认发现项 → 发现文档对应条目状态改为"已确认"
  * 用户要求调整 → 回对应阶段
* 提交
  * 用户明确许可后执行 git commit
  * **禁止**未经用户许可执行 git commit
* 更新开发文档
  * 操作对象：步骤文档 + 发现文档
  * 执行者：@orchestrator
  * 删除临时实现细节，只保留目标与关键产出摘要，并引用对应的 commit 提交
* 反思
  * 目标：优化 Skill 
  * 回顾上下文窗口，反思这次任务执行时出现的失误或者顺利执行的经验
  * 在 session 中告知用户即可

### 注意事项

#### 处理子代理的空值返回：

* 至少对那个没有返回值的子代理重试一次。不行的话再向上报告此次异常

### 发现文件的创建与维护

* 创建者：编排者
* 创建时机：对应步骤开始写代码时
* 写入者：编排者
* 内容来源：
  * @fixer 在 task result 中报告的原始发现
  * @oracle 在审查报告中列出的自己的发现以及理解
  * @explorer 在探查报告中列出的发现
  * 编排者在协调过程中自己注意到的
* 编排者职责：收到报告 → 复核/判断分类（bug / 改进 / 不确定）→ 整理并写入文件 → 告知用户

## 开发启动协议

**每次开始开发的事，按顺序执行：**

1. `git log --oneline -10` + `git diff --stat` — 了解整体进度和未提交改动
2. 利用 `glob` 工具查找项目已有的 `00-总纲.md` 文件的文件路径
3. 询问用户
    1. 如果只定位到一个总纲文件，跳过询问用户这个阶段
    2. 如果用户没有进一步指令，向用户展示当前已有的总纲文件（如果没有，请告知用户应该怎么做；）
    3. 如果用户有进一步指令，根据指令推断需要使用的总纲文件，如果不确定找到了，如实告知
4. 执行 `bash .opencode/skills/planning-with-files-omo-slim-general/scripts/dev-status.sh <总纲文件路径>` — 交叉验证步骤状态（活跃步骤、脏标记、待确认发现项）
5. 根据 dev-status.sh 输出的 `🔥` 步骤，read 对应的步骤文档和发现文档

此序列确保：不用盲目遍历文件，先拿到全局视图，再精确 read 当前活跃的文件。

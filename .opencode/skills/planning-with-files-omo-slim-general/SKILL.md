# 利用文档，搭配 OMO-slim 进行开发规划的通用版本

## 设计思想（为什么这样设计——推理时以此为判断标准）

* AI 做任何**无人**监督的决定后必须确认：因为 AI 无法替用户判断需求正确性，
  用户确认是唯一的方向纠偏点；不确认的决定用户看不见、无法审查，错误方向会浪费整个执行阶段。
* 利用好 Git 和硬盘上的文件：因为上下文窗口易失、跨 session 无法延续；
  文件持久、可 diff、可回滚，是跨 session 协作的唯一可靠载体。
* AI Agent 执行流程透明、可理解：因为用户靠书面契约审查，
  透明才可审查、可追溯、可信任。
* 每种文件只有一个明确的读者与时机：步骤文档给人对齐意图，提示词文档给 agent 作为执行契约，发现文档给后续 agent 与工程师作为上下文。写文件前先问"给谁看、何时看"——各文件的边界规则（步骤文档不写验收标准、提示词必须自包含零歧义）都由此推出。

## 使用前提

### 适用此模式的场景

- 新增功能模块
- 新设计模式引入
- 旧代码重构（中大型）
- 危险的 BUG 修复（可能破坏旧有功能）

### 绝对不要用的场景

- 逻辑简单清晰的问题
- 单文件修改或双文件机械迁移（小型重构）
- 快速查询
- 代码问答

## 四种核心文件

| 文件 | 规则 |
|------|------|
| 总纲 | 与 `步骤/`、`发现/`、`提示词/` 同级，文件名为 00-总纲.md |
| 步骤 | `步骤/{编号}-{名称}.md`，发现文档与之同名 |
| 发现 | `发现/{编号}-{名称}.md` |
| 提示词 | `提示词/{编号}-{名称}/`下，目录以步骤编号开头 |

例子：
```markdown
docs/开发文档/<阶段名>/
├── 00-总纲.md
├── 步骤/
│   └── 04-<步骤名>.md          ← 步骤文档
├── 发现/
│   └── 04-<步骤名>.md          ← 发现文档（文件名与步骤文档相同）
└── 提示词/
    └── 04-<步骤名>/
        └── 04.6-<提示词名>.md     ← 提示词文档
```


### 总纲文档

* 定义：步骤文件的统领，阶段性对应的总纲文件
* 功能：
  * `dev-status.py` 脚本用于对开发文档的定位与处理
  * 人类对总体进度的把控

### 步骤文件

* 定义：在具体开发任务前 AI 与用户共同商讨过后制定的文件，
* 功能：交付给用户看的，用来给用户判断实行细节是否合意的

### 发现文件

* 定义：在开发过程中完全由 AI 顺手发现并记录的文件
* 功能：既可以给 Agent 确定问题上下文，也可以给人类工程师判断系统问题
* 创建时机：在开发过程中 subagent 发现任何问题或改进点时，立即按步骤创建或更新此文件

### 提示词文件

* 定义：由@orchestrator 交付给@fixer /@designer的主要提示词，是执行阶段的输入契约，是给 Agent 执行契约与详细执行方案

## 典型工作流

### 基本框架

```
    载入 skill
  → 开发启动协议

  → 用户指明方向
  → (探索 & 厘清现状) / 与用户讨论 / Web 搜索已有设计
  → session 内给出更加详细的设计方案

  → 撰写步骤文档
  → 用户确认（文档）
  → 撰写提示词文件
  → 用户确认（可选）

  → 执行 & 简化（可选） & 验证& 更新发现文档(重复执行)

  → 用户检查（代码）

  → 拟提交 & 用户确认
  → 执行 commit & 更新步骤文档 & 总纲文档（可选）

  → 反思（可选）
```
注1：没有画出回流
注2：只有用户明确说明“继续”类的提示词后才能执行（如执行，提交）。因为修改后用户可能还会进行多处修正
注3：“&”表示连续串行步骤，而不需要用户监督
注4："/"表示根据实际需要，灵活改变步骤方法

### 工作流的核心内容

* 讨论：
  * 目标：得到详细，明确的**功能需求**，确保你将要实现和是用户想要的完全一致
  * 方法论：
    * 讨论**不过多**涉及代码细节
    * 不确定的功能需求一定要询问。一次只询问一个问题，可以同时说说你的建议
    * 给出最终完整，详细的功能需求前，否则一定不要进入下一步写正式文档
  * 讨论结果输出：session 内一个更详细，有更多细节考量的设计方案
    * 用自然语言陈述
    * 可以用字符画阐述
* 规划与编写文档
  * 产出：步骤文档 / 提示词文档
    * 步骤文档写在对应开发阶段的 `步骤/` 子目录下，提示词文档写在对应开发阶段的 `提示词/` 子目录下，作为单独文件
    * 提示词文档也是贯穿执行与验证的契约。用户确认，执行，验证阶段共用同一份（同一份才能保证验证的就是执行时那份要求——契约不漂移）
* 用户确认
  * 用户确认后进入执行
  * 默认等待用户确认（方向纠偏点——不确认的决定用户看不见，错误方向会浪费整个执行阶段）
* 执行
  * 执行期间各 specialist 报告的发现由 @orchestrator 实时收集，执行完后立即更新发现文档（执行中上下文最新鲜，晚记录等于丢失——发现的时效性）
* 简化
  * 读取对象： git diff + 项目根目录级 CLAUDE.md / AGENT.md（注意，这里没有提示词文档，注意提醒@cleaner 不要去履行@oracle 的职责）
  * 执行者：@cleaner
  * 代码质量提升，代码可理解性提升
  * 不确定应不应该改或者清理 → 向上报告
* 验证
  * 读取对象： 发现文档 + git diff + 项目根目录级 CLAUDE.md / AGENT.md
  * 执行者：@oracle
  * 读取对象：代码
  * 传入@fixer 执行阶段时的**同一份提示词文档**作为审查契约（契约不漂移——验证的必须是执行时那份要求）
  * 审查不通过 → 回@Orchestrator原委派对象（@fixer/@designer）执行；提示词 本身有误 → 回规划
* 用户检查
  * @orchestrator 暂停，等待用户检查代码
  * 步骤文档 + 发现文档一并呈现，检查发现文档为可选
  * 用户确认发现项 → 发现文档对应条目状态改为"已确认"
  * 用户要求调整 → 回对应阶段
* 提交
  * 用户明确许可后执行 git commit
  * **禁止**未经用户许可执行 git commit
* 更新开发文档
  * 操作对象：步骤文档 + 发现文档
  * 执行者：@orchestrator
  * 删除临时实现细节，只保留目标与关键产出摘要，并引用对应的 commit 提交并合并到上一步的文档提交中
* 反思
  * 目标：优化 Skill 
  * 回顾上下文窗口，反思这次任务执行时出现的失误或者顺利执行的经验
  * 在 session 中告知用户即可

#### 关于 subagent 的 task 返回值

编排者收到 @fixer 结果后：
* 确认自检清单完整性（所有修复项均已打勾或说明未完成原因）

编排者收到 @oracle 审查结果后：
* 审查全通过 → 进入更新文档阶段
* 审查不通过 → 按回流建议派原执行者重做或回规划修 提示词
* 有不通过并且非不确定项 → 按回流建议派原执行者重做或回规划
* 发现报告归入发现文档，编排者复核分类后写入

### 其他注意事项

#### 处理子代理的空值返回：

* 至少对那个没有返回值的子代理重试一次。不行的话再向上报告此次异常

#### 分派任务时直接引用已经编写好的提示词文档地址！

* 分派具体任务给 subagent 时不要重新完整的写一份提示词
* 包括 @designer，@fixer，@cleaner，@oracle
* 否则 subagent 的表现可能会欠佳、费 token，且重写会让契约漂移、验证失去依据（契约不漂移）

#### 发现文档的更新时机

* 每当 subagent 完成任务并上报时就记录（执行中上下文最新鲜，晚记录等于丢失——发现的时效性）

## 开发启动协议

**每次开始开发的事，按顺序执行：**

1. `git log --oneline -10` + `git diff --stat` — 快速了解整体进度和未提交改动
2. 利用 `glob` 工具查找项目已有的 `00-总纲.md` 文件的文件路径
3. 如果意图不明确，询问用户意图
4. 执行 `python3 .opencode/skills/planning-with-files-omo-slim-general/scripts/dev-status.py <总纲文件路径>` — 交叉验证步骤状态（活跃步骤、脏标记、待确认发现项）
5. 根据 dev-status.py 输出的 `🔥` 步骤，read 对应的步骤文档和发现文档

此序列确保：不用盲目遍历文件，先拿到全局视图，再精确 read 当前活跃的文件（状态从文件推导，不靠记忆）。

## 参考提示词契约

默认规则：没有触发词 → 停在当前阶段，不推进，并询问用户意图（停下问比猜着推进便宜——猜错方向的成本远高于问一次的对话成本）。

* 讨论下吧/你怎么看 -> 和用户进行讨论
* 写总纲/步骤/发现文档 -> 进入规划阶段，撰写对应名称的文档（不多做）
* 执行 -> 进入执行阶段
* 简化 -> 进入简化阶段
* 验证 -> 进入验证阶段
* 提交 -> 拟提交代码，等待用户确认
* 反思 -> 进行反思（可选）

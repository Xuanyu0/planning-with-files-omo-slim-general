## 解释

* 文件命名：`提示词/<步骤文档名>/<步骤编号>.<子步骤编号>-<提示词名>.md`（如 `提示词/04-<步骤名>/04.6-<提示词名>.md`），标题使用完整二级编号
* 具体内容（书写时按此顺序）：
  * **当前状态**：可以简述当前的问题以及对应的文件下的代码状态，为 Agent 指明问题方向
  * **目标**：完成后系统的状态，转写自步骤文档对应子步骤的目标
  * 架构变更（可选）：若涉及架构调整，用字符画呈现。
  * 具体子任务：进一步说明每个子任务需要干什么，编号与步骤文档孙步骤编号一致（如 1.1、1.2）
  * 新增/修改文件：以表格的格式列出所有涉及文件，每个文件附带简要职责说明。
  * 变更边界：明确禁止修改的文件、模块、函数。这是契约的红线。
  * **验收标准**：对应核心任务的每一项制定执行者/审查者可自行验证的完成条件列表。无验收标准的提示词不得交付执行。
  * subagent task 的返回内容要求。
  * 不确定事项（可选）：本次 提示词 书写过程中产生的不确定事项。

## 提示词写作规范说明

* 语言风格
  * **断言式**：已确定决策用直接陈述。
  * **尽量不解释"为什么"**
  * **新旧对比**（可选）：如需架构变更，必须先画`旧：`再画`新：`，让读者一眼看出变化。不要混着描述。
  * **文件清单表格**：单独成节。
  * **验收标准可验证**：用 md 的 check-box 风格书写
* 禁止项
  * 在提示词中贴完整代码块
  * 指定精确行号修改
  * 给出完整搜索字符串
  * 留"详见对话记录"这类外部引用 — 提示词必须自包含，零歧义

### 特定对象的提示词编写规范

* 针对@fixer
  * 改动规则描述到"函数级"或"逻辑块级"，不到"行级"
  * 涉及多个文件的紧耦合改动（写端和读端必须同步）放一个 fixer 任务，不拆分
  * 纯机械替换（如全局重命名）可描述到"符号级"
* 针对@designer
  * 描述用户可见的交互意图和视觉目标，不描述 CSS / 布局实现
  * 给出设计约束
  * 视觉风格由 designer 自行决定，编排者只审查是否符合约束
